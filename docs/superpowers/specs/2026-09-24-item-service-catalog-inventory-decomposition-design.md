# Marketing 商品目录与渠道库存并入 item-service 设计

## 1. 目标与边界

本设计定义 Marketing 拆分第二阶段中与身份/RBAC 数据迁移相互独立的一条路径：将 Marketing 商品目录、SKU 和渠道库存能力并入已有 `item-service`。这是十个业务服务拆分计划中的一个阶段，不代表整体拆分已完成。

本阶段目标是让 `item-service` 成为商品/SKU 及渠道库存的唯一最终所有者，同时保留现有 Marketing API 的外部兼容性，并确保现金购买、积分兑换和库存预占语义不变。

当前仅形成边界和迁移设计，不实施代码迁移、数据库回填、API 路由切换或身份/RBAC 迁移。Marketing 继续作为现有功能的唯一活动写入方，直到未来阶段通过数据、权限、兼容性和回滚验收后再单独批准切换。

## 2. 当前结构与证据

| 能力 | 当前位置 | 现状及设计影响 |
| --- | --- | --- |
| 商城商品/SKU | `item-service` 的 `Item` 与 `item` 表 | 现有模型以 `item.id` 标识商城商品/SKU，并包含名称、分价（分）、库存、图片、分类、品牌、规格、状态和审计字段。需作为既有商城目录兼容边界。 |
| Marketing 商品目录 | Marketing `Product`、`ProductSku` | 产品和 SKU 是独立标识域；SKU 另有 SKU 编码、现金价格、积分价格、购买方式开关、状态和版本。Marketing 现金下单与积分兑换会读取商品/SKU 快照。不得假设 Marketing ID 与 `item.id` 相等。 |
| 渠道库存 | Marketing `sku_inventory`、`inventory_channel_stock`、`inventory_reservation`、`inventory_ledger` | 维护总量、渠道分配、预占/确认/释放/退回及幂等流水。该状态机必须整体迁移并保留原子更新语义。 |
| 抽奖奖品库存 | Marketing 抽奖奖品库存实现 | 是奖品发放域的独立库存事实，不等同商品可售库存；本设计不迁移该能力，也不将其与商品库存合并。 |
| 消费方 | Marketing 现金订单与积分兑换 | 当前通过本地 Catalog/Inventory 服务调用读取可购 SKU 并预占库存。跨服务调用要在消费者迁移阶段通过 `hm-api` 契约完成，不允许直接读取 `item-service` 数据库。 |

Marketing V1–V28 已发布迁移保持不变。后续若需为 `item-service` 建立 schema，只新增该服务自己的迁移，不复用或改写 Marketing 历史迁移。

## 3. 目标边界与标识映射

1. `item-service` 是商品目录、SKU 和渠道库存的最终数据与写入所有者。迁移完成后，不保留第二份可独立编辑的 Marketing 商品目录或库存写入路径。
2. 复用现有商城商品标识作为目标规范标识，但必须通过显式、可审计的 Marketing 商品/SKU 到商城 `item.id` 映射完成归并。映射关系和映射规则须由只读数据审计及业务确认确定；不能仅凭 ID、名称或 SKU 编码猜测，也不能在本设计中臆定一对一关系。
3. 映射审计发现一个 Marketing SKU 对应多个商城 item、多个 Marketing SKU 竞争同一 item、属性/价格冲突或无法解释的历史引用时，暂停该记录及相关切换；不得自动改 ID、合并账号/商品或丢弃记录。
4. 目标模型应保留现有商城字段，并仅增加经消费方确认仍需支持的 Marketing 元数据或兼容投影。现金价、积分价及购买开关属于销售策略；若不适合成为通用 `Item` 字段，应在 `item-service` 自己的 schema 中建模，不复制一份独立可写目录。
5. 订单、积分兑换、履约和对账所需的商品、SKU、价格与物流快照仍须在交易发生时固化到各自业务记录中；后续商品编辑不得改写历史快照。

## 4. API 与授权兼容

迁移设计须保持现有公共请求和响应兼容：`/api/products/**`、`/api/admin/products/**`、`/api/admin/inventory/**` 路径、`ApiResponse` 包装、分页字段、状态码和错误语义。在单独批准的切流阶段之前，不变更 Gateway/Nginx 路由，也不把管理端路径提前暴露给 `item-service`。

迁入后的管理写接口必须由目标服务本身执行服务端权限校验。当前共享 `hm-security` 已提供可信用户上下文，但不应据此推断 `CATALOG_READ`、`CATALOG_MANAGE`、`INVENTORY_MANAGE` 权限校验已在目标服务落地。相关权限能力、失败关闭行为、审计身份及权限缓存策略须在身份/RBAC 前置审计与后续权限设计完成后验证。权限缺失时不得切换管理路由或以 Gateway 认证代替业务授权。

本阶段不迁移用户、角色、权限或角色关联数据，不改登录流程或认证路由。身份/RBAC 预检仍是独立门禁；不能把商品迁移设计当作其审计结果。

## 5. 库存状态与一致性不变量

目标实现必须保留现有库存业务的不变量和可观察行为：

- SKU 总库存、渠道分配量、可用量、预占量和已确认消耗量之间的约束及原有业务校验；
- 预占只能沿合法状态迁移（`RESERVED` → `CONFIRMED` 或 `RELEASED`），终态不得被重复或反向推进；
- 按业务单号的唯一性/幂等语义，以及初始化、分配、预占、确认、释放、退回等台账操作；
- 对渠道可用库存的条件更新必须保持原子性，不能以读后写替代原有并发保护；
- 失败重试及重复调用的返回语义需通过迁移前后的契约测试固定。

渠道库存能力与商品目录一起归入 `item-service`，但与订单、积分账户等其他服务保持服务边界。跨服务数据库外键、直接写库和双写均不允许。抽奖奖品数量、抽奖 Redis Lua、配额键、Redisson 锁、TTL 与对账逻辑完全不在本设计范围内，须保持原状。

## 6. 消费者与契约

当前现金购买、积分兑换和其他 Marketing 下单流程依赖本地目录和库存服务。未来消费者迁移时应在同一交付阶段提供并验证 `hm-api` 提供方/消费方契约，包括商品/SKU 查询、价格/购买资格快照、库存预占及其确认/释放接口。只在确有提供方和消费方落地时增加契约，不先创建空接口。

调用方迁移后，目录读取和库存命令由 `item-service` 提供；订单/积分服务不直接访问其数据库。契约必须明确调用超时、幂等键、失败重试和错误映射，避免网络重试造成重复扣减或状态不一致。

## 7. 数据迁移、切流与回滚门禁

切流前需完成以下事项并留下可复核的脱敏证据：

1. 在获批的只读数据库账号下完成 schema 与数据聚合审计，明确商品/SKU 映射、重复/冲突、状态分布、库存总量和台账差异。不得把逐行用户名、手机号、密码散列、凭证或逐行账号映射写进 Git、报告或交接材料。
2. 业务负责人确认映射及保留/处置规则；所有歧义记录均有明确处理结论。任何无法解释的 ID 冲突、SKU 关联或库存不平衡都是停止条件。
3. 在 `item-service` 新增独立、可从空库初始化的 schema 迁移；定义可重跑、可审计的数据搬运方案、计数/余额校验和回滚方案。回填获批前不执行任何写入。
4. 完成服务级权限校验、API 兼容、库存并发/幂等、从零建库以及消费者契约测试。未获批准不得启动 Compose 或其他状态化服务来代替所需审计。
5. 切换窗口内由单一所有者写入：先校验目标数据与服务就绪，再按获批的原子操作切路由并禁止 Marketing 旧写路径。禁止新旧服务长期双写或以“影子写”改变库存状态。
6. 切流验收比较映射覆盖率、目录状态、库存余额、未终结预占、台账业务单号及 API 行为，并演练恢复单一写入者的回滚。无法保证切回后无并行写入时不得切流。

只读预检目前未运行时，后续文档应如实记录环境前置条件缺失；不能把“使用 Docker”视为启动服务或使用应用账号的授权。数据库可达性、审计凭证和执行批准必须分别确认。

## 8. 测试与验收

本设计阶段只做文档审阅，不运行应用、容器或数据库。未来迁移验收至少包括：

- 商品、SKU、状态、销售策略和 API 页面/详情兼容测试；
- 库存状态转换、渠道隔离、重复业务单、并发预占、确认/释放重试及失败恢复测试；
- 新目标 schema 从空库安装及迁移重跑/审计测试；
- `hm-api` 提供方与现金购买、积分兑换消费方的契约测试；
- 目标服务权限允许/拒绝/上下文缺失测试；
- 切流前后聚合计数、库存余额、未终结预占和台账幂等键核对，以及路由/单写入者回滚演练。

单元或纯逻辑测试可先行，但不能替代获批的数据库审计、服务级验证和生产切换门禁。

## 9. 明确不在本阶段范围

- 身份/RBAC 数据迁移或身份歧义处置；
- 任一数据库账号创建、权限修改、用户数据写入或历史数据回填；
- Gateway/Nginx 登录、认证或 RBAC 路由切换；
- Marketing 商品/库存代码删除，或宣称 Marketing 已完成整体拆分；
- 抽奖奖品库存及 Redis Lua、配额键、Redisson 锁、TTL、对账逻辑的任何变更；
- 对 Marketing Flyway V1–V28 的改写；
- 为本设计启动 Compose、应用进程或其他状态化服务。

## 10. 待确认问题

- 数据审计确认 Marketing Product/ProductSku 与商城 `item` 的实际映射基数、冲突和历史引用后，采用何种目标关联模型？
- 商品实体和 SKU 是否严格一对一，还是现有商城 `item` 实际代表 SKU？哪些 Marketing 属性必须进入目标服务，哪些仅属于订单/积分业务快照？
- 库存 ledger 中 `sku_id` 与 `hmall_item_id` 两类标识的历史数据如何按审计结果归一？不得在拿到脱敏聚合及业务确认前预设规则。
- `CATALOG_*`、`INVENTORY_*` 权限在身份/RBAC 审计完成后由哪个已验证的服务端组件强制执行？权限服务暂不可用时目标管理写接口如何失败关闭？
- 现金订单、积分兑换以及其他消费方分别在哪一阶段切换到 `hm-api`，其库存预占状态由哪个服务负责协调？
- 如何在回滚窗口中阻止目标服务与 Marketing 同时写入，并对已发生的库存命令进行无损恢复？
