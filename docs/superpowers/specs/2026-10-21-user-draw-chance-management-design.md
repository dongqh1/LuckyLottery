# 用户管理中的抽奖机会管理设计

日期：2026-10-21

## 目标

把管理员对用户抽奖机会的查询、调整和流水查看放入用户管理页。每行提供“管理机会”入口，管理员按需打开具体用户的机会账户。

## 当前情况

- `users.html` 已列出用户 ID、用户名和手机号，但没有抽奖机会信息。
- `marketing.html` 有一块独立的抽奖机会面板，需要管理员手动输入用户 ID。
- lottery-service 已提供管理员账户查询、流水分页和人工调整接口，并校验管理员白名单。
- 机会账户响应包含可用和预留余额；流水响应包含业务类型、业务编号、方向、数量、余额变化、操作人、原因和时间。

## 设计

- 在 `users.html` 用户表格增加“抽奖机会”操作列，每位用户显示“管理机会”按钮，并将当前行的用户 ID 和用户名带入管理弹窗。
- 管理弹窗按需调用已有接口读取该用户账户和第一页流水；展示可用机会、预留机会、增加/扣除表单及分页流水。
- 调整表单要求正整数数量和原因；成功后刷新余额和第一页流水。重试同一笔失败请求时复用 `adjustmentId`，表单内容变化后生成新的 ID。
- 流水展示时间、业务类型、业务编号、增加/扣除、数量、变动后可用/预留余额、操作人及原因。
- 继续使用现有管理员会话令牌和 lottery-service API，不增加批量查询接口，不在用户列表加载时对每个用户逐个请求。
- 从 `marketing.html` 和 `marketing.js` 移除独立的用户机会查询/调整面板及对应状态和方法。奖品类型 `DRAW_CHANCE`、抽奖机会账户后端逻辑和其他营销功能保持现状。
- 对 HTTP 403、用户不可用、余额不足和网络错误显示可理解的提示。

## 验收标准

1. 用户列表每一行都有“管理机会”入口；打开后展示与该用户绑定的账户余额和流水。
2. 管理员可以增加或扣除正整数机会并填写原因；调整成功后余额和流水同步刷新。
3. 扣除余额不足、非管理员或用户不可用时展示服务端错误，不伪报成功。
4. 切换用户后弹窗显示新用户的数据，不残留上一个用户的余额或流水。
5. 营销管理页不再出现按用户 ID 管理抽奖机会的独立区域。
6. 用户分页查询不触发每行一次的机会账户请求；用户主动打开弹窗时才加载数据。
7. 新增前端测试覆盖弹窗入口、账户/流水查询、调整幂等请求以及旧营销区域移除。

## 范围外

- 不修改 lottery-service 数据模型、管理接口和数据库。
- 不恢复每日抽奖上限，也不修改普通抽奖、奖励发放、Outbox 或 RabbitMQ 流程。
- 不把抽奖机会余额直接塞入用户服务的用户列表响应。
