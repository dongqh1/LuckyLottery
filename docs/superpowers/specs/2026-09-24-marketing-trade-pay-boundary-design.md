# Marketing 订单与支付归并至 trade/pay-service 设计

状态：用户已确认进入实施计划阶段；设计仍未实施。

## 1. 目标与范围

本设计细化 Marketing 拆分总设计的“订单与支付归并”阶段：现金订单由 `trade-service` 唯一拥有，支付单及支付生命周期由现有 `pay-service` 唯一拥有。两者只经业务 API 和版本化消息协作，不共享 Mapper、实体或数据库写入。

本设计只明确边界、兼容约束和实施门禁，不迁移代码或数据，不新建/修改数据库账号，不启动 Compose/应用，不切换 Gateway/Nginx 路由，也不启动 user-service 身份/RBAC 迁移。Marketing 继续是旧流程唯一写入方，直到未来单独批准并验收切换。

## 2. 现状与依据

| 领域 | 当前实现 | 对拆分的影响 |
| --- | --- | --- |
| Marketing 订单 | `mall_order` 使用字符串 `order_no`、用户 ID、价格快照、支付期限和订单状态；同一模块还实现超时取消。 | 订单状态与金额的最终所有权应归 trade；pay 只能取得可信的可支付订单快照并请求受保护的状态转换。 |
| Marketing 支付 | `payment_order` 使用字符串 `payment_no`/`order_no`、`BIGINT amount_cent`、`PENDING/SUCCESS/FAILED` 状态和回调结果。 | 这些外部业务标识和历史状态必须显式映射，不能假设与 pay-service 的数值型支付号或业务订单 ID 相同。 |
| Marketing 支付成功 | 回调锁定支付单和订单，核对用户/金额，随后确认库存、核销优惠券、更新订单/支付状态；实物订单还创建物流单并关联回订单。 | 这是跨订单、支付、库存、优惠券和履约的流程，不是单纯搬动一张支付表。各步骤的新所有者、原子性、幂等与补偿需先明确。 |
| 现有 pay-service | `pay_order` 使用数值型 `bizOrderNo`、`payOrderNo` 和 `Integer amount`；通过 `TradeClient` 查询可支付订单、确认订单支付，余额支付后写支付成功 Outbox。 | 可复用的边界已经存在，但其 ID/金额表示及余额支付语义不能直接代表 Marketing 模拟支付语义。 |
| API/授权 | Marketing 用户模拟、管理模拟依赖现有登录上下文和 RBAC；模拟回调签名使用仅限本地的固定秘密。 | 本设计不改变路由或授权。任何未来回调暴露/免 JWT 规则都须单独审查；Gateway 认证不能替代服务端 RBAC。 |

依据文件包括总设计 `2026-09-23-marketing-service-decomposition-design.md`、`marketing-service` 的 V13 和 `PaymentServiceImpl`，以及 pay-service 的 `PayOrderServiceImpl`、`TradeClient` 合同和现有 trade/pay 边界计划。Marketing Flyway V1–V28 均保持不变。

## 3. 目标所有权

- `trade-service` 是 Marketing 现金订单、订单价格/商品/地址快照、支付截止时间、取消与“待支付→已支付”条件状态迁移的唯一所有者。订单读写均由 trade API 执行。
- `pay-service` 是支付尝试、支付号、支付渠道/结果、回调状态、支付成功时间及支付成功 Outbox/消费幂等记录的唯一所有者。支付状态只由 pay API 更新。
- `item-service`、优惠券的当前所有者/后续 `coupon-service`、以及后续 `fulfillment-service` 分别拥有库存、券、履约状态。trade/pay 不直接读取或写入这些服务的表。
- `marketing-service` 在切换前保留完整旧实现且是唯一写入方；切换某个能力时必须在同一受控阶段停止旧写路径，禁止长期双写。

支付单与业务订单只以稳定业务引用相关联。跨服务接口传递的必须是业务快照或状态命令，不传 `Order`、Mapper、表实体或 SQL。最终规范 ID、字符串业务号的保留方式及历史支付号映射均由只读聚合审计和批准规则决定。

## 4. 目标交互约束

1. 创建支付单时，客户端金额不是权威数据。pay 必须取得 trade 返回的、归属该用户且仍可支付的订单快照，以订单应付金额创建支付单；重复请求须按稳定支付/订单业务键校验身份和结果。
2. `PROCESSING`、失败、成功及终态重放须保留 Marketing 已有的状态冲突和幂等语义。成功回调必须核验签名、支付号、订单归属、金额和订单状态；并发成功只能产生一次业务支付成功效果。
3. trade 使用条件状态迁移确保订单仅从允许状态进入已支付；迟到回调、取消竞争、金额不一致或身份不符必须失败关闭或按已批准的幂等结果返回。
4. 库存确认、优惠券核销和实物履约各由其服务 API/事件完成。不得由 pay 直接写对应数据库，也不得因迁移省略现有业务效果。
5. 支付成功消息须有稳定事件 ID、版本和可核对的业务引用；消费者须以事件/业务键幂等。Outbox 仅保证消息与 pay 本地事务，不能宣称同时原子提交 trade、库存、券或履约。

### 支付尝试、超时和迟到成功

- Marketing 以 `payment_no` 做支付请求幂等，而 V13 对 `order_no` 只有非唯一索引；不能假定一单只有一条支付记录。目标 pay 模型必须能保留同一订单的多次支付尝试及各自历史状态，不能把多条记录折叠成一个当前状态。用现有 `pay_order` 加外部尝试键还是新增独立尝试实体，留待合同与数据审计后确定。
- 订单支付超时取消由 `trade-service` 调度并通过条件状态迁移完成；它还须以稳定业务键幂等地请求 pay 关闭仍未成功的支付尝试。订单取消和支付成功竞争时只能有一个订单状态迁移获胜，关闭命令不得覆盖已成功的支付事实。
- 若回调确认支付成功，但 trade 因订单已取消、金额/用户不一致或暂时不可用而无法完成订单迁移，pay 必须保留已验证的成功事实和可重试的业务事件，不能把真实成功改记为失败或静默丢弃。trade/pay 要隔离并告警不可自动收敛的冲突；退款、人工处理或其他补偿规则须经业务批准后另行设计。回调响应只有在能清楚区分“支付已确认”和“订单/履约已完成”时才可对外返回，旧 DTO 是否需扩展须在兼容评审中确定。

### 一致性决策门

当前 Marketing 在同一旧服务内完成支付回调副作用；拆分后需要在以下方案中作出经业务确认的选择，不能由实现者隐式决定：

| 方案 | 好处 | 代价/门槛 |
| --- | --- | --- |
| 同步命令并使用 Seata AT 协调必须共同提交的数据库参与者 | 更接近旧回调的同步可见结果；订单/支付状态的失败可同步返回。 | 每个参与者须支持并验证 Seata；HTTP、RabbitMQ、Redis 和外部副作用仍不具事务原子性；参与者增加会扩大故障面。 |
| Pay Outbox 驱动 trade 状态机及后续域命令/事件，以幂等和补偿收敛 | 服务拥有权清楚，故障可重试，避免跨库长期锁定。 | 旧流程回调响应与订单/库存/履约完成之间可能出现可见延迟；必须定义查询状态、重复/乱序、超时和补偿语义。 |

推荐先保留已有 pay→trade 条件业务 API 的明确边界，并用故障矩阵比较同步协调和 Outbox/补偿；只有在回调响应语义、库存/券失败恢复及履约触发规则得到确认后，才锁定具体一致性方案。此处未批准前不写代码级迁移步骤。

## 5. 标识、状态与金额映射门禁

- Marketing `payment_no`、`order_no` 为字符串；现有 pay/trade 合同使用数值型订单 ID 和支付 ID。先确定稳定业务键/API 查询方式，保持前端与回调所需字符串不丢失；不得仅靠相同数字部分推断等价。
- Marketing `amount_cent` 为 `BIGINT`，目标 pay `amount` 为 `Integer`。在只读审计后验证实际范围并批准单位/溢出规则；不能隐式窄化或换算。
- Marketing `PENDING/SUCCESS/FAILED` 与 pay `NOT_COMMIT/WAIT_BUYER_PAY/TRADE_CLOSED/TRADE_SUCCESS` 不是一一对应。需要明确未提交、处理中、失败可否重试、取消/超时和终态规则；不得按枚举序号直接复制。
- `callback_result`、`failure_reason`、`paid_at`、创建/更新时间、唯一键及支付成功 Outbox/消费幂等历史都须列入聚合核对；历史回调明细和凭据不进入 Git 或交接文档。
- 在获批的 SELECT-only 审计账号和可读 schema 条件满足前，不连接数据库、不执行 SQL、不填写任何实际映射/数量，也不把 Docker 可用性视作权限证明。

## 6. API、安全与兼容

Marketing 原有 `/api/payments/**`、`/api/admin/payments/**`、`/callbacks/payments/**` 及 JSON 包装/字段/错误语义在本设计阶段保持不变。未来切换后由 `pay-service` 提供这些支付兼容 API，将旧外部合同转换成 pay/trade 业务合同；不得让新服务依赖 Marketing 包或直接复用旧实体。切换前 Marketing 继续按现状写入，不提前做代理或双写。

不在本阶段改变 Gateway/Nginx 路由、登录/RBAC、JWT 豁免、回调认证或模拟权限。当前固定签名秘密仅说明本地模拟行为，不可作为生产级回调认证。路由切换前须分别验证 JWT/授权边界、回调验签与重放防护、用户本人范围和旧客户端合同；Gateway 认证不得替代 pay 服务自身的授权/回调验证。

## 7. 实施前置与停止条件

开始代码/数据迁移前必须逐项通过：

1. 身份/RBAC 和目录/库存审计门禁按其各自报告完成；未运行审计保持未运行，不能以静态测试代替。
2. trade/pay 的业务键、订单快照和所有者 API 已定稿；目标 pay schema 的迁移/演进机制已查明并通过空库安装验证。`pay-service` 资源中尚未发现独立 migration 目录；根 `mysql/migrations/V007`、`V008` 是 schema-init 脚本且包含创建/修改服务账号、权限和 schema 的操作，不能作为只读审计手段执行。
3. SELECT-only 聚合审计及业务确认给出用户/订单/支付映射、状态分布、金额范围、重复/孤立关系和未终结单处理规则；任何歧义或溢出风险都停止相关迁移。
4. 回调成功一致性方案、Seata 参与者或 Outbox/补偿责任、库存确认/券核销/履约所有者、乱序和重试语义有明确决策及回滚方案。
5. 新旧支付/订单 ID 和外部业务号兼容策略、切换期间单一写入者、幂等键及历史查询行为经测试验证；不允许复制权限、自动改 ID 或自动合并业务记录。
6. API/RBAC/回调安全审查、提供方/消费方契约测试、并发/重复回调与支付-取消竞争测试、事件重复/乱序/失败补偿测试、脱敏计数与金额对账均通过。路由回滚演练属于之后单独批准的切换阶段门禁，不是本设计阶段的执行项。

若发现身份歧义、状态无法映射、金额超出目标范围、支付/订单孤儿记录或下游副作用无可靠恢复路径，只记录聚合结论并暂停；不改数据、不复制权限、不切流。

## 8. 不在本设计范围

- 本地/远程数据库连接、SQL 审计执行、账号创建或授权变更、数据回填；
- user-service 身份/RBAC 迁移、登录兼容和任何 Gateway/Nginx 路由切换；
- Marketing 代码删除、Flyway V1–V28 改写、支付渠道接入或支付模拟语义变更；
- 以 Seata 假设覆盖 Redis、RabbitMQ、HTTP 或第三方副作用原子性；
- lottery-service 及其 Redis Lua、配额键、Redisson 锁、TTL 和对账逻辑的任何改动；
- 宣称 Marketing 已完成十个业务微服务拆分。

## 9. 验收标准

本设计完成时只表示服务边界和门禁可供评审，不表示迁移已启动。批准后另行编写小步实施计划，并在每一步按范围执行合同测试与构建。实际数据切换必须等第 7 节所有门禁通过并单独批准；Marketing 旧实现仅在新所有者验收和回滚演练通过后移除。
