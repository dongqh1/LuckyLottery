# 抽奖管理简化设计

日期：2026-10-21

## 目标

1. 管理员在一个“奖品”流程中完成奖品展示信息和实际发放内容配置，不再先建奖励、再填写奖励 ID 建奖品。
2. 管理员可查询某个用户的奖励抽奖机会，并为该用户增加或扣除机会；不恢复每日抽奖上限。
3. 保留现有抽奖订单、奖励快照和 Outbox/RabbitMQ 发奖链路。

## 当前结构

- `reward_definition` 保存发放内容：奖励类型、目标 ID、数量和配置快照。
- `marketing_prize` 保存抽奖展示信息：奖品名称、等级、图片、说明及其奖励定义关联。
- `marketing_activity_prize` 保存某个活动中的权重和库存。

奖励定义和奖品不是完全相同的数据职责，但管理端强迫管理员分两次创建并手工关联 ID，造成了重复操作。抽奖资格校验、中奖快照和发奖事件目前会读取奖励定义。

抽奖机会账户已经有可用余额、预留余额和流水表；账户更新采用 MySQL 事务和行锁。流水目前没有人工调整原因和操作人字段。Gateway JWT 目前只传递用户 ID，没有管理员角色声明。

## 设计

### 单次创建奖品

- `marketing.html` 只显示一个“奖品管理”区域和一个创建表单。
- 表单包含奖品名称、类型、等级、图片/说明、是否可叠加，以及实际发放所需的目标和数量。
- 前端不再出现“创建奖励”、奖励 ID 查询/输入或两步工作流。
- 后端在一个事务中创建内部奖励定义和奖品，并自动生成唯一奖励编码；奖品接口接收发放信息，不要求客户端提供奖励定义 ID。
- 奖励定义继续作为内部发奖配置，由现有抽奖快照和 Outbox 事件使用；不删除数据库表、历史奖励 ID 或履约校验。
- 活动奖池仍单独设置中奖权重、库存和展示顺序。
- 移除独立奖励定义管理页面/路由；仅保留内部创建逻辑。

### 管理奖励抽奖机会

- 在抽奖管理页面新增“抽奖机会”区域。管理员输入用户 ID 后查看可用余额、预留余额和分页流水。
- 管理员可以选择增加或扣除、填写正整数数量并填写原因。扣除只针对可用余额，余额不足时拒绝且不修改账户；预留余额不允许手工修改。
- 人工调整和流水写入在同一 MySQL 事务中，复用账户行锁，并使用 `MANUAL_ADJUSTMENT` 流水类型。
- 流水增加 `operator_user_id` 和 `reason` 字段；通过新 Flyway 迁移添加可空列，以保留已有记录。
- 调整请求带唯一 `adjustmentId`，将其作为流水业务 ID，以数据库唯一键实现重试幂等；重复 ID 携带不同用户、方向或数量时返回冲突。
- 后端提供管理员账户查询、流水查询和调整接口；前端展示调整前后结果及错误信息。

### 管理员校验

- 页面隐藏或禁用按钮不构成权限控制，调整接口必须由后端校验。
- 当前 JWT 没有角色字段，因此本次在 lottery-service 增加管理员用户 ID 白名单配置 `LOTTERY_ADMIN_USER_IDS`。本地种子管理员 ID 1 可作为默认开发配置，部署环境可以覆盖；没有可信用户上下文或用户 ID 不在白名单时拒绝访问。
- 白名单校验仅用于新增抽奖机会管理接口，不扩展为全项目权限重构。

## 不在本次范围

- 不恢复活动每日抽奖次数限制。
- 不用 Redis Lua 管理人工抽奖机会余额。
- 不将奖品库存改成 Redis 预占；现有 MySQL 条件扣减继续负责奖品库存正确性。
- 不删除 `reward_definition` 表或改动营销服务数据模型。

## 验收标准

1. 管理员只需一个表单即可创建可绑定进活动奖池的奖品；请求和页面均不要求输入奖励定义 ID。
2. 新建奖品的类型、目标和数量能进入现有中奖快照及履约消息。
3. 管理员可按用户 ID 查看账户和流水；增加/扣除会更新可用余额并记录操作人、原因及调整后余额。
4. 余额不足的扣除不会产生余额变化；同一个 adjustmentId 重试不会重复增减。
5. 非白名单用户不能调用抽奖机会管理接口。
6. 普通抽奖不受每日次数限制；活动奖池、Outbox 和 RabbitMQ 发奖流程保持工作。
